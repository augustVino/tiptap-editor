工作流程中其实缺少了一部分：

1. 对前端页面进行 API 调用链分析、对每个字段的消费场景进行梳理。（此过程中沉淀了多个 command 指令）
2. 通过 Claude code 自动操控浏览器，对网页（面试快（b 侧）首页）中每个字段的消费场景进行截图。（此过程中沉淀了多个 skill 工具：mult-chrome、chrome-cdp、kill-chrome 等）。
3. 通过 claude code + feishu cli 工具，把本地 md 文档更新到飞书文档。

这部分很重要，体验出了在 AE 转型过程中 AI 协同提效是很大的，尤其是过程中产出的 command/skill 沉淀，是可以复用到多个场景中的，比如刚刚提到的 skill:

- mult-chrome: 打开多个浏览器实例，每个实例隔离，独自使用一套 host 环境。这就解决了 switchHost 的一个痛点（切换 host 全局生效，chrome 浏览器通常会有 dns 缓存，清理麻烦）。

- chrome-cdp: 连接到打开的浏览器实例，操控页面 UI 交互、获取控制台日志。这对于开发、debug 问题时很有帮助。

- kill-chrome: 关闭对应的浏览器实例，释放资源。

这几个 skill 可以单独使用，也可以按序组装成工作流。比如我最近做的 AiChat 中有个多功能的输入框，这个输入框支持通过@、/来触发快捷指令或者引用，交互很复杂，考虑到日后使用场景应该会很多，防止重复造轮子，我就封装了一个。但是时间原因我又没办法对所有的交互场景进行测试，所以我是这样指挥 claude code 做的：

1. 基于 @src/ 实际源码为我补充测试 demo ，毕竟现有 demo 中只是覆盖了几种简单的使用，并不能包含所有的场景，而通常用户是挑剔的，他们可能会有各种奇奇怪怪的用法（因为 SDK 提供了这个 api，他们就会进行 api 的各种组合），所以我要保证各种场景的运行正常。

2. 基于组件 API 和现有的测试 demo，为我创建多个测试用例文档，要求覆盖所有的执行路径，每个文档中包含测试目标、输入、步骤和预期结果。覆盖所有的业务逻辑和 UI 展示。

3. 使用多个 subagent ，用 mult-chrome 启动多个浏览器实例，每个实例对应一个 @examples/demos/ 中的 demo，然后使用 chrome-cdp skill 按照 @examples/test-features 中对应 demo 的用例文档进行操作，完成测试后输出一个总结文档。

结果就是 claude code 开启了九个浏览器实例，每个跑一套用例，最后全部结束后输出一份总结报告，汇总了每个用例的测试结果，并且整体分析后给出了整体的测试通过率。
